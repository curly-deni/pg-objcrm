# Мини CRM 2B Studio

Приложение для ведения объектов и задач. Постановщик управляет объектами, задачами и исполнителями. Исполнитель работает только со своими задачами. Роли и права проверяются в PostgreSQL.

## Локальная разработка

Требуются Node.js 24, npm и Docker-совместимый runtime для локального Supabase. Приложение и Supabase запускаются раздельно: CLI сам управляет своими контейнерами, Vite запускается на loopback адресе.

```sh
npm ci
npm run supabase:start
npm run local:reset
npm run dev
```

Для ежедневного запуска с остановкой Supabase при выходе из Vite используйте `npm run dev:local`. Окружение доступно по `http://127.0.0.1:5173`; Supabase API — по `http://127.0.0.1:54321`, Studio — по `http://127.0.0.1:54323`, PostgreSQL — по `127.0.0.1:54322`.

`seed.json` содержит всю конфигурацию демо: пользователей, объекты, задачи, назначения и последовательности смены статусов. При первом `local:reset` файл создаётся автоматически со случайными паролями. Он добавлен в `.gitignore`; можно заменить email и пароли в одном файле перед следующим сбросом. Шаблон находится в `seed.example.json`. Не публикуйте `seed.json`.

`local:reset` очищает локальную базу, применяет миграции и заново создаёт набор из `seed.json`. Для API-проверок выполните `npm run test:api`. Для остановки локального Supabase отдельно выполните `npm run supabase:stop`.

## Проверки

```sh
npm test
npm run test:unit
npm run test:coverage
npm run test:api
npm run typecheck
npm run build
npm run format:check
```

`npm test` запускает unit/component-набор и затем интеграционные проверки. Unit/component-тесты охватывают восстановление сессии и профиль, маршрутную защиту, формы, доступные по ролям действия, список задач, навигацию и запросы TanStack Query. `test:coverage` формирует HTML-отчёт в `coverage/` и проверяет минимумы: 70% строк и операторов, 60% ветвлений, 65% функций.

API проверки используют реальные Supabase Auth сессии демопользователей и проверяют RLS, SQL-привилегии, запрет подмены автора, переназначение, статусы, историю и мягкое удаление. Service role нужен только для создания временного Auth аккаунта без профиля. Запросы к CRM выполняются через обычные пользовательские сессии. Service role хранится только в локальном `.env.local`.

Для форматирования используйте `npm run format`. Prettier сортирует Tailwind классы и форматирует SQL.

## GitHub Actions и публикация

Workflow `CI` запускается на каждый push и pull request в `main`. Он проверяет форматирование, типы, компонентные тесты с порогами покрытия, миграции и RLS на локальном Supabase, затем делает production build.

Публикация не запускается на push. На вкладке **Actions** вручную выберите `Deploy Supabase migrations` или `Deploy Vercel production` и введите идентификатор целевого проекта. Оба workflow доступны только для `main`, повторно проверяют проект перед публикацией и запускают полный набор тестов. Supabase сначала показывает список миграций, затем применяет их. Для Vercel автодеплой от Git отключён в `vercel.json`; production разворачивается только этим workflow.

Перед первым запуском добавьте в GitHub:

- Secrets: `SUPABASE_ACCESS_TOKEN`, `SUPABASE_DB_PASSWORD`, `VERCEL_TOKEN`.
- Repository variables: `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`.
- GitHub Environments `supabase-production` и `vercel-production`. Рекомендуется ограничить их веткой `main` и включить обязательное подтверждение ответственного.

Токен Supabase и пароль базы берутся в настройках проекта. Создайте scoped access token Supabase с правами на чтение проекта и запись базы. Vercel token ограничьте нужной командой и проектом. В production Environment Vercel должны быть настроены `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`; они подхватываются через `vercel pull` во время ручной сборки. Не добавляйте ключ Supabase `service_role` ни в Vercel, ни в клиентское приложение.

CLI Supabase закреплён lockfile на версии 3.0.0. Команда remote push явно указывает `--remote` и `--yes`, так как CLI v3 по умолчанию работает с локальной базой и требует явного подтверждения для автоматизированного изменения удалённой базы.

## Интерфейс и переводы

Интерфейс использует `i18next` и `react-i18next`. Сейчас доступен только русский язык; строки собраны в `src/i18n/locales/ru.json`. Счётчики используют правила русской множественной формы i18next (`1 задача`, `2 задачи`, `5 задач`). Чтобы добавить язык, нужно добавить ресурс и включить код языка в конфигурации `src/i18n.ts`.

## Облачная база данных

Проект `objcrm-2b-studio` создан в Supabase, миграция схемы применена. Приложение не публиковалось.

Чтобы подключить CLI к проекту, войдите в Supabase и выполните `supabase link --project-ref xsnxbcuazkgddtegosrg`. Для последующих версий схемы используйте `supabase db push`. Регистрацию пользователей и анонимный вход отключите в настройках Auth. Аккаунты и роли создаются административно; service role никогда не задавайте с префиксом `VITE_`.

## Публикация

Публикация в Vercel пока не выполнялась. В проект Vercel позднее нужно добавить только `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`, выбрать сборку `npm run build` и каталог `dist`. `vercel.json` перенаправляет глубокие клиентские маршруты на `index.html`. Роли, пароли и `SUPABASE_SERVICE_ROLE_KEY` в Vercel передавать нельзя.
